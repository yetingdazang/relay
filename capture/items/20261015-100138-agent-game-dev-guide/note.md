## 最值得采用的开发技巧

本节是结合官方文档和个人小游戏场景整理的建议，不是性能提升的实验结论。

### 1. 先把“玩家要做什么”说清楚
比“做一个精致、有趣的游戏”更有效的需求是：玩家怎样操作、遇到什么阻碍、如何得分、怎样失败、多久一局。先完成一个核心循环，例如“移动躲避 → 收集道具 → 得分 → 失败重开”；再加关卡、成长或内容。

第一版建议只做一个场景、一种主要操作和完整重开流程。目标是能实际玩到，而不是功能清单很长。OpenAI 的游戏开发案例也从具体体验和小型可玩版本出发。[S2]

### 2. 给任务写清目标、相关信息、约束与验收
这四项来自官方提示建议。[S1] 对小游戏可写成：

| 项目 | 例子 |
| --- | --- |
| 目标 | 调整跳跃手感，使连续跳跃更容易控制 |
| 相关信息 | 当前版本、问题发生的场景、截图或录屏、相关角色控制文件 |
| 约束 | 保留现有操作方式和美术风格 |
| 验收 | 能连续跳过三个平台；失败后可以正常重开 |

给结果留判断依据，不必先替 Agent 设计所有内部实现。大功能先让它给出简短方案；小改动可以直接实现。

### 3. 一轮集中解决一个可以验收的问题
例如一轮调跳跃，一轮修结算，一轮改背包布局。玩法、UI、美术同时变化时，很难判断哪项改动导致手感或错误。

让 Agent 完成“定位 → 修改 → 相关验证”再交付。遇到卡住的错误，先要求复现和解释原因，再继续补丁；避免越修越多却始终没有复现依据。

### 4. 调参集中管理，比不断改代码更省事
把移动速度、跳跃高度、敌人生成间隔、伤害、奖励等放进少量明确的配置项，并标出单位和影响。后续可以直接要求“提高加速感，同时缩短停下来的距离”，由 Agent 调整参数并验证效果。

不要把大量未经确认的参数都做成玩家设置。开发调试面板只在开发环境按需启用，正式界面保留玩家需要的选项。

### 5. 把游戏状态和界面显示分开
开始、游玩、暂停、结算应有清楚的状态转换；界面显示依赖游戏状态。这样改血条或按钮布局时，较容易保留计分和胜负逻辑。

需要重点关注的小游戏问题：暂停后计时或刷怪继续运行、重开后旧事件重复触发、失败画面还能操作角色、分数或道具在重开时没有正确清理。让 Agent 针对改动检查相关状态即可。

### 6. 让 Agent 能复现问题并观察结果
提供启动方式、触发步骤、控制台报错，以及必要的截图或短录屏。浏览器游戏可以按需增加固定随机种子、快速进入测试场景、只在开发环境开放的状态读取入口。

官方案例通过可重复场景、状态信息和浏览器测试检查游戏。[S2] 对你的小项目，不必照搬大型调试系统：能快速回到出错现场最有用。

截图主要帮助判断视觉；真实点击、键盘输入和状态变化才帮助判断能否玩。直接设置“胜利状态”的测试，不能替代从游玩到胜利的完整验证。

### 7. 测试力度跟随改动，减少无意义的反复检查
文字或配色修改：打开对应画面，确认布局与可读性。
操作、暂停或结算修改：实际走一遍相关流程。
存档、经济或核心规则修改：补充相关边界用例，验证旧数据和关键状态。

已有相关检查通过，且没有新修改或疑点时即可收尾；不用每轮都全库审计、全套重跑或增加一组重复测试。交付只需说明最终行为、验证结果与确实未解决的问题。

### 8. 保留简短规则与稳定版本
把启动方式、重要目录、界面文案偏好和常见错误写进短小的项目 AGENTS.md；资料较多时按主题链接出去。官方建议保留可复用规则，同时避免指令与文档过量加载。[S1][S3]

完成稳定里程碑时留一个 Git 提交；试验大改版前保留可回退版本。按一个连贯目标组织对话，目标切换或状态明显混乱时再交接，不必按固定压缩次数强制换窗。

## UI 与视觉设计怎么推进

### 从参考图变成可实现的规则
先找 2—3 张同类游戏界面，标明每张图借鉴什么，例如血条位置、背包分组或按钮层级。参考混得越多，Agent 越容易把不同风格拼到一起。

再做一张简单布局图，确定主区域、常驻信息和弹窗。用 Penpot 或直接画草图都可以；关键是信息位置和操作关系清楚。

把“更高级一点”改成可观察要求：“主操作按钮更突出”“减少常驻说明文字”“背包每行四格”“提示不遮挡角色”“受击反馈短暂且可关闭强烈效果”。视觉方案确认后再扩展到其他画面。

### 小游戏 UI 的六个实用原则

| 原则 | 实际做法 |
| --- | --- |
| 信息有优先级 | 游玩时优先呈现生命、目标、必要资源；次要说明放帮助或首次引导 |
| 元素统一 | 选一个字体组合、一套图标和间距规则；状态色保持一致 |
| 状态有反馈 | 按钮按下、选中、禁用可区分；得分、受击、失败及时反馈 |
| 文字易读 | 在实际窗口和手机尺寸查看中文、数字与长标题；检查溢出和过小字号 |
| 操作符合设备 | 手机检查触控位置与误触；键盘检查焦点、暂停和返回 |
| 动效服务操作 | 先做命中、得分、菜单切换等反馈；逐步增加装饰，观察清晰度和流畅度 |

### 针对你偏好的界面文案
可以在项目规则中保留下面这段简短约定：

~~~text
界面文案服务玩家操作、规则理解和状态判断。
开发过程、实现细节和改动说明放在交付消息中。
同一功能的解释集中到必要位置，避免重复小字。
本轮未要求新增教程或说明区时，沿用现有信息结构。
注释主要解释代码中不明显的原因。
交付说明聚焦最终行为、相关验证和必要限制。
~~~

需要说明规则时，优先通过首次引导、帮助页或明确状态提示解决；让主界面保持清楚。

### 素材怎么保持一致
先选一套主体美术，再补缺少的图标或音效。角色、场景和按钮同时混用多个素材包，很容易产生比例、描边和光照差异。

需要生成原创图片时，给出同一份风格说明、参考图、用途、尺寸、背景与视角要求。概念图可以决定方向，进入游戏前仍需检查透明边缘、切帧、碰撞区域和尺寸。严格整齐的精灵帧与 UI 组件，优先考虑现成素材、矢量或代码绘制。

## 实用网站清单

下面的“用法”是针对本任务的建议；网站功能依据各自官网核验。先使用标注“优先”的站点，其他按缺口补充。

| 网站 | 最适合解决什么 | 怎么用 | 费用或素材注意点 |
| --- | --- | --- | --- |
| **优先：[Interface In Game](https://interfaceingame.com/)** | 主菜单、背包、HUD、设置、结算的布局参考 | 按界面元素查同类案例，选少量截图并写明借鉴点 | 网站用于参考；截图及游戏内容属于各自权利人，不作为可直接搬用素材 [S4] |
| **优先：[Kenney](https://kenney.nl/assets)** | 角色、场景、UI 等基础素材 | 优先下载同一套素材搭可玩原型，再统一配色和尺寸 | 官方资产页面素材为 CC0，可商用且无需署名；仍保留包内许可文件 [S5] |
| **优先：[itch.io Game Assets](https://itch.io/game-assets)** | 找更具体风格的 UI 包、像素角色、地图和音频 | 按 UI、Sprites、Tileset、Pixel Art 和价格筛选 | 免费、付费均有；是否可用及署名等条件看具体作者页面与许可 [S6] |
| [Game-icons.net](https://game-icons.net/) | 技能、武器、状态和道具图标 | 选 SVG 或 PNG，统一颜色、背景与尺寸 | 主页标明 CC BY 3.0，使用时保留作者与许可信息 [S7] |
| [Lospec Palette List](https://lospec.com/palette-list) | 像素风配色不统一 | 先选一套色板，把对应颜色值交给 Agent 用于角色、场景和 UI | 色板可按颜色数或标签筛选；案例图另看使用条件 [S8] |
| [Penpot](https://penpot.app/) | UI 布局、组件与交互原型 | 先排主菜单、游玩界面、暂停和结算；截图与尺寸规则一起交给 Agent | 开源设计平台，官网提供免费注册；托管方案等看当前页面 [S9] |
| [Photopea](https://www.photopea.com/) | 裁图、调整尺寸、图层处理与 PSD 编辑 | 修改按钮、背景和角色素材，导出项目所需图片 | 浏览器图像编辑器，可免费使用；导入素材的许可另核对 [S10] |
| [Piskel](https://www.piskelapp.com/) | 像素角色、小动画和精灵图 | 修改现有角色帧，实时预览，再导出精灵图 | 免费在线编辑器，支持 GIF 和 spritesheet PNG 等导出 [S11] |
| **优先：[Jfxr](https://jfxr.frozenfractal.com/)** | 拾取、跳跃、命中等短游戏音效 | 生成几个统一风格的音效，试听并控制音量 | 作者说明生成的声音可商用且无需署名 [S12] |
| [Freesound](https://freesound.org/) | 环境声、脚步和其他录制音效 | 按声音用途检索，试听后记录来源与许可 | 单条许可有 CC0、CC BY、CC BY-NC 等区别，选择符合项目用途的文件 [S13] |

针对你做小游戏的情况，建议先用 **Interface In Game + Kenney + itch.io + Jfxr**：布局、美术包与声音先齐备，遇到具体缺口再加工具。

如果要 Agent 帮你找素材，给它明确的画风、视角、尺寸、预算和使用用途，要求列出候选包的来源与许可。页面能够读取，不等于已经下载了完整素材；确认集成时要核对实际文件。

## 一轮开发的实用流程

1. **定范围**：写清一个核心操作、胜负条件、目标设备和本轮完成标准。
2. **做可玩版本**：使用占位素材，打通进入、游玩、失败或胜利、重开。
3. **定视觉**：挑少量参考，确定布局、色板与素材包。
4. **边玩边改**：每轮只给一个主要问题，用位置、触发步骤和期望效果描述。
5. **相关验证后保存**：检查本轮涉及的真实流程，保留稳定版本与少量下一步事项。

完成一个目标后再开下一轮；将“玩法是否有趣”和“界面是否好看”分别记录，避免每次把两个问题一起改。

## 可复制的任务提示词

以下是任务模板，需要替换方括号中的内容；不会因为保存在笔记里而自动执行。

### 开始一个小游戏
~~~text
在当前项目中做一个 [类型] 小游戏，面向 [电脑/手机/两者]。
核心循环：[操作 → 阻碍 → 奖励 → 失败或胜利]。
第一版范围：[一个场景、必要操作、计分、暂停、重开等]。
先确认现有技术栈和启动方法。需要方案时给出简短建议，
然后完成一个能实际游玩的版本。
验收：[具体可观察行为]。
界面采用 [风格]，文案简洁，开发说明放在交付消息中。
完成后运行项目并验证本轮涉及的操作，报告实际结果。
~~~

### 修改 UI
~~~text
修改 [具体画面] 的 UI，参考附件 A 的 [布局] 与附件 B 的 [配色]。
本轮目标：[更突出主要按钮/重排背包/提高可读性]。
保留既定玩法和视觉风格。
界面所需元素：[列出]；尺寸或排列要求：[列出]。
分别查看 [实际桌面尺寸] 与 [实际手机尺寸] 的结果，
检查文字溢出、点击区域和遮挡，提供最终画面与相关验证。
~~~

### 修复 bug 或调整手感
~~~text
问题：[实际表现]。
复现步骤：[进入场景 → 操作 → 出错]。
期望：[明确行为或希望产生的体验]。
相关材料：[报错/截图/录屏/文件]。
先复现并定位原因，做范围明确的修复，再按同一路径验证。
检查受影响的状态转换；通过后给出简短结果。
若仍不能复现，说明缺少哪一项证据，不连续猜测补丁。
~~~
