# Vibe coding 应该养成的四个好习惯：小黑盒帖子摘要

> [!summary] 提要
> 作者建议通过复用现成方案、适时换对话、按需读取资料、定期复盘，改善 AI 编程的效率与连续性。核心是把可复用的经验和项目状态保存下来，减少对长对话的依赖。本文是原帖观点摘要，具体换窗阈值和效果属于作者经验，尚未独立验证。

## 原文四个建议

### 1. 开发前先找现成方案
让 AI 先检索 GitHub、相关社区和技术讨论，寻找可复用项目、已有实现和问题解决办法，减少重复开发。作者举例提到用 Codex 检索 Linux.do，以及通过 GitHub 授权辅助搜索项目、查看 issue 和 PR。

### 2. 在阶段闭环后考虑换对话
作者认为，同一对话连续使用很久、反复压缩上下文，可能让任务状态混淆并降低效率。他给出的参考触发点是完成约 2—3 个独立功能、经历约 2—3 次压缩、连续工作约 60—90 分钟，或切换项目与独立目标时，评估是否新开对话。

同一功能的实现、测试和修复通常作为一个完整阶段，不必因小步骤频繁换窗。交接摘要保留目标、范围、验证结果、未完成项、必要运行状态、授权依据和文件入口；依靠项目持久记忆续接，不复制全部聊天历史。观察不到的次数和时长不应编造。

### 3. 按需检索资料
先使用已有且有效的信息；需要定位时先读项目索引，大文件先查标题或关键词，再读相关片段。只有证据不足、信息冲突，或任务本身需要整体审计时，才扩大阅读范围。

阅读清单应帮助定位，不能变成所有文件全文必读。项目当前状态、运行验证、设计决策和历史追溯分别按任务取用；适用规则与安全边界仍须读取。

### 4. 定期复盘并固化经验
分析一段明确范围内的成功与失败任务，提取高频需求、反复返工原因、模型常见错误和用户操作习惯。把重复工作固化为 skill，把需要约束的行为写进 AGENTS.md，并更新项目文档和持久记忆，使经验可在后续对话中复用。

## 复盘与蒸馏怎么做

作者提出分两步处理：

1. 先用成本较低的模型分类任务，整理代码、界面设计、检索、常见错误等材料，形成带索引的报告。
2. 再由能力更强的模型分析代表性样本，提出针对全局规则、项目文档、用户习惯和持久记忆的改进。

作者建议参考任务之后的用户反馈：一次通过可作为正面案例，多轮返工仍不满意可作为反面案例。重点是形成可执行改进，而非保存大量聊天记录。

## 阅读判断

以下为摘要整理者的判断，与原文观点分开：

- 这篇文章最有价值的主线是“先复用、保留状态、控制阅读范围、持续复盘”，适合作为个人开发流程的检查思路。
- “压缩 5—6 次就容易遗忘”“长对话越来越费 token”及具体换窗次数，是作者观察，不宜视为所有模型和产品的统一规律。
- 用户紧接着的一条反馈可用于筛选复盘样本，但不能单独证明代码正确或任务质量；正反案例仍需结合实际验收结果。
- 原帖介绍的是工作流经验，本文没有据此修改任何 AGENTS.md、创建 skill 或执行笔记中的建议。
