# 半年超深度使用 Agent 攻略分享——如何全面解放自己的生产力？

> [!summary] 一句话结论
> 文章记录了作者在约半年内从网页聊天式 AI，逐步走向 **知识库（Obsidian）＋ 可操作本地项目的 Agent（Claude Code/Codex）＋ 外部工具接口（MCP）＋ 可复用流程（Skill）** 的过程。核心变化不是“模型换强了”，而是 AI 从问答助手升级为了解工作背景、能调用工具、能产出成果的协作系统。

## 一、作者的实践演进（按原文顺序）

### 1. 网页版对话式 AI：有能力，但每次都得重新解释
作者最初使用聊天 AI 搜索资料、起草文案、制作图片，需要自己审核、反复说明任务。最大瓶颈是换新窗口后项目和偏好无法延续；作者由此提出“怎样让 AI 记住我的需求”的问题。

### 2. Cherry Studio＋自定义知识库：拥有私人上下文
作者转向 Cherry Studio，接入可自定义的模型 API、上传个人和开发资料，并收集开发者文档组成知识库。改进之处是回答能引用个性化材料；但作者遇到上下文限制、长文本质量问题、绘图不顺手，以及一次会话难以自动接续任务的问题。作者提出要找能持续执行、理解文件的系统。

### 3. VS Code＋Claude Code＋Skills：由回答问题转为执行任务
作者经过学习部署 Claude Code，获得以下能力：按需求进行网络调研并形成报告；使用/安装 Skills；直接读取目录里的文档并排版；辅助素材、图文与流程制作。作者仍抱怨 Windows 命令行错误、需要手动转移不同平台的需求、知识库要反复解释、工具后台难操作且工作流半自动。因此继续寻找更顺手的整体方案。

### 4. Obsidian：把个人知识系统变成 Agent 可读的项目资料
作者参考关于“Obsidian＋Agent”的资料建立知识库。初期觉得 Obsidian 的设置很繁琐，后来改用 Claude 协助部署，并把**优先查询知识库**的要求写入项目记忆；之后将 Obsidian 用于文章撰写、知识管理和未来的写作素材。
**关键点：** Obsidian 提供易读、可维护的 Markdown 笔记；Agent 的行为规则还需单独设定。不是安装 Obsidian 就自动拥有长期记忆。

### 5. Codex、Claude Code 与多模型协作：建立自己的工具
作者开始使用 Codex 等工具，尝试开发一键分发、特色内容排版、渠道跟踪等功能，发现开发便利，但遇到后台复杂、工具衔接不够紧密和大量人工介入的问题。文中提及 GPT、Claude、GLM、Kimi、DeepSeek 等模型，但没有提供可复现的横向基准评测。

### 6. 最终形态：MCP＋自制 Skill＋知识库＋云文档
作者把浏览器后台交给 MCP 工具操作，将反复执行的步骤封装为 Skill，配合知识库、素材库和云文档读写接口，尽量将调研、排版、制图和发布串成连续工作流。原文给出的典型过程是：
- **内容需求**：人先写一段需求 → AI 规划工具与步骤、给出方案 → 人修改并确认 → AI 调用 Skill/MCP 产出和检查 → 人验收后发送或发布。
- **执行需求**：人描述需要做的事项 → AI 先给执行方案 → 人核验 → AI 调用接口执行；必要时调用设计工具或生成工具补足素材。

作者称其当前有多类内容生产、渠道同步、调研和发布工作由 AI 辅助，重点已转向把精力放在**方向、方案和最终结果**上，而不是手工完成每一个细节。

## 二、可迁移的核心方法

1. **知识与记忆外置**：项目背景、决策、偏好、素材和处理结果写入可持续维护的 Markdown/知识库，而不是全指望对话窗口记忆。
2. **任务从讨论转成执行**：每个任务包含目标、输入来源、操作边界、可用工具、验收条件与交付格式；Agent 先计划、再执行、再报告。
3. **Skill 只封装重复而稳定的流程**：例如“读需求→调研→生成报告→自检→保存”，避免为一次性小事无意义地开发插件。
4. **MCP 用于接通真实系统**：当需要访问云文档、浏览器后台、素材平台时通过受限接口连接；Skill 是“怎么做”，MCP 是“能连接、能操作什么”。
5. **人机分工要清晰**：作者反复提到人工核对方案、调整审美要求和检查结果。发表、删除、支付等高风险动作应保留确认。
6. **先解决真正的阻塞点**：作者每一步升级都起源于旧流程的具体限制（上下文、文件读取、工具操作、流程中断），而非纯粹追逐新模型。

## 三、给 Relay / Codex / Obsidian 的落地借鉴

以下为**结合本仓库现状的延伸建议**，不是原作者已经为 Relay 设计的内容：

| 作者做法 | Relay 可采取的实现 |
| --- | --- |
| 知识库随工作持续增长 | 手机 Obsidian 写入 `notes/`，Git 同步到 Relay；Codex 按项目需要读取对应笔记 |
| 每次打开新对话不用重讲背景 | 在 `AGENTS.md` 明确“先查任务相关知识摘要”，仅检索相关目录，不无差别读取整个库 |
| 需求先审核再执行 | 继续沿用 `inbox/` 任务单中的 `execution_policy`，区分只分析、安全修改与允许执行 |
| 将重复工作封装 | 等真实重复需求明确后，把 browser / Playwright、资料整理、报告检查做成可复用的 Skills |
| 工具连接与知识管理解耦 | MCP / API 用于访问网站与云端工具，Obsidian 负责可检索的笔记，Codex 负责执行 |
| 自动沉淀执行结果 | Codex 完工后更新交接任务状态，在 `notes/02-Projects/` 留下简要决策、成果和踩坑记录 |
| 素材文件不断增长 | GitHub 仅保留笔记与索引；图片/PDF/视频逐步迁往独立对象存储，GitHub 预览分片短期使用后清理 |

**推荐优先级：**
1. **先完成 Codex 的“查相关笔记 → 执行授权任务 → 写回项目摘要”闭环。**
2. 确认浏览器自动化真实任务的需求与安全边界，再做单一可复用 Skill。
3. 接入云文件/浏览器接口；最后完善跨设备自动调度及独立附件存储。

## 四、需要保持谨慎的地方

- 文中“每天使用超过 12 小时”“消耗大量 Token”“三成工作由 AI 辅助”等是**作者自述**，不能直接作为一般人的效果保证或投资回报依据。
- 对不同模型、上下文容量、绘图能力及具体工具的评价属于作者当时的体验，可能随版本、环境变化。
- 自动完成不代表零人工：原文中的关键方案核验、素材选择和发布验收仍然有人参与。
- “只要把知识库接到模型就能记住一切”并不准确：需要可靠的检索入口、访问权限、更新机制与上下文控制。
- 不建议把隐私文档、账户令牌、登录态直接写进知识库；应采用独立密钥管理和最小权限。
